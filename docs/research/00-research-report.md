# Ship a Backendless, View-Only PixelLab Gallery

> Design names and defaults were finalized later (provisional name "Vitrine"; unofficial, not affiliated with PixelLab); see [docs/design/00-decision-log.md](../design/00-decision-log.md).

A fully client-side Svelte 5 gallery for PixelLab assets can be built today without a proxy or backend. PixelLab's REST v2 and MCP endpoints accept cross-origin requests from any origin. Its media host serves every image with `Access-Control-Allow-Origin: *` and a one-year cache. Official character ZIP and sprite-sheet exports download without a token ([02](02-browser-integration-and-security.md); [R1](../reviews/R1-research-cross-review.md)). The binding constraints lie elsewhere. The user's token is one account-wide bearer secret with no scopes. Asset UUIDs are permanent no-auth download keys that survive token rotation. The Creator gallery and maps are reachable only through MCP tools that return prose written for language models. Animation frames appear only in per-asset detail responses, with no timing, so the app must fall back to the 8 fps that PixelLab's own players use. Read rate limits are unpublished ([01](01-pixellab-api-asset-inventory.md); [09](09-verification-followups.md)). The product opportunity is large. PixelLab's website spreads a user's assets across at least seven libraries, hides card actions and animation behind mouse hover, caps bulk export to one asset type at a time, and gives Creator images no URL ([03](03-pixellab-website-gallery-audit.md)). The design that wins follows the model Apple and Google both settled on after public backlash: a flat Library grid plus a second tab for collections, named Folders in the final design. It draws every sprite at a whole number of device pixels with `image-rendering: pixelated`, and it ships on plain Vite 8, Svelte 5, and TypeScript 6 with four small runtime libraries ([04](04-platform-gallery-apps-ux.md); [06](06-pixel-art-rendering-animation-and-export.md); [07](07-tech-stack-and-architecture.md)). Before any code depends on those answers, a half-day "Phase 0" with a real token must measure read cost, rate limits, and REST image hosts, and confirm that the one MCP image tool has no side effects ([R1](../reviews/R1-research-cross-review.md)).

## PixelLab serves seven asset families over REST and two more only through MCP

The public contract is the REST v2 API at `api.pixellab.ai/v2` plus an MCP server at `api.pixellab.ai/mcp`. Both take the same `Authorization: Bearer` token. On 2026-10-18 the live OpenAPI had **102 paths and 275 schemas** ([OpenAPI](https://api.pixellab.ai/v2/openapi.json); [01](01-pixellab-api-asset-inventory.md)). REST has JSON list and get routes for **seven families: characters, objects, top-down tilesets, sidescroller tilesets, isometric tiles, Tiles Pro, and UI assets**. Every list pages with `limit` and `offset`, returns a `total`, and has **no search, tag, status, sort, or project parameter**. The page maximum is 100, except sidescroller tilesets and Tiles Pro, which cap at 50 ([09](09-verification-followups.md)). So search, filtering, and sorting must happen client-side over a synced index. The cheapest token check is `GET /v2/balance`. It is free and read-only, returns the credit balance, subscription plan, and remaining generations, and answers `401 {"detail":"Invalid API token"}` for a bad token. No endpoint on either surface returns an email, username, or user ID, so "who is signed in" can only be shown as plan and balance ([02](02-browser-integration-and-security.md)).

The MCP server is **stateless Streamable HTTP**. A browser POSTs one JSON-RPC message and always gets back `text/event-stream` with a single `data:` frame. No `Mcp-Session-Id` is issued, `GET` returns 405, and `tools/call` works without `initialize` ([MCP docs](https://api.pixellab.ai/mcp/docs); [MCP transports spec](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports); [02](02-browser-integration-and-security.md)). The unauthenticated tool list holds **103 tools, none with an `outputSchema`**. Results are human-readable text plus image blocks, so a browser client is about 40 lines over `fetch`, but every parser of that text is brittle and unversioned ([01](01-pixellab-api-asset-inventory.md); [09](09-verification-followups.md)). MCP is the only public path to two families: the **Creator gallery** (`list_images`, `get_image`) and **Map Workshop maps** (`list_maps`, `view_map`).

Media delivery is friendlier than the documentation implies. Almost every image lives on `backblaze.pixellab.ai` (Cloudflare in front of Backblaze B2) at **unsigned, non-expiring URLs**. They send `ACAO: *` even on a 404 and `Cache-Control: public, max-age=31536000`, and the `?t=` parameter is a cache-buster rather than a signature ([02](02-browser-integration-and-security.md); [R1](../reviews/R1-research-cross-review.md)). The OpenAPI examples name `supabase.pixellab.ai` and `cdn.pixellab.ai`, but spike 09 found both dead: Supabase answers "Bucket not found" and the CDN host does not resolve. Backblaze is the live host. Whether REST bodies use it too still needs one tokened call ([09](09-verification-followups.md)). There are three exceptions. The REST getters for top-down tilesets and isometric tiles return base64 and should be avoided. The **Creator gallery `download_url` is an S3 SigV4 presigned URL with a 7-day expiry and no CORS headers, and its preflight returns 403**, so the app must take gallery pixels from `get_image`'s inline frames instead ([01](01-pixellab-api-asset-inventory.md)). Spike 09 settled how those frames are laid out. The `WxH` printed by `list_images` is the **per-frame size**, reversing spike 01's doubt. The stored sheet is a row-major grid that is sometimes a strip and sometimes 3×3 or larger, and the list does not say which. Per-frame inline images are therefore the only safe source ([09](09-verification-followups.md)).

The metadata has real gaps. **No character, object, or gallery animation carries an fps or frame duration anywhere in the public contract.** Characters and objects expose no seed and no model. Only characters have `updated_at`, and only characters and objects have `tags` ([01](01-pixellab-api-asset-inventory.md); [OpenAPI](https://api.pixellab.ai/v2/openapi.json)). A schema check by R1 found that **`ObjectSummary` has no `group_id`**, so characters can group into one card per state group but objects cannot without fetching every detail ([R1](../reviews/R1-research-cross-review.md)). For timing, a static read of PixelLab's production JavaScript shows the defaults. The character-detail player defaults to `frameRate: 8`. The Creator gallery player is labelled "8 FPS" and the Creator GIF export writes 125 ms per frame. Exceptions are library-card hover at 5 fps, object detail at 150 ms, VFX at 12 fps, and talking animations at 90 ms. **8 fps (125 ms) is therefore the best-supported default**, superseding the 10 fps that spike 06 and R1 proposed before this evidence existed ([09](09-verification-followups.md); [PixelLab site](https://www.pixellab.ai/)).

Several things users see on the website have **no public read path at all**: VFX "My effects", the font library, portrait conversions, the portrait attached to a character, vocal and lip-sync sheets (reachable only per character through `get_lip_sync`, which has not been exercised), uploads, map JSON export, and Game Builder project membership. Fonts and portraits exist only as job rows that disappear about 8 hours after the job finishes ([01](01-pixellab-api-asset-inventory.md); [09](09-verification-followups.md)). Projects deserve a specific warning. REST has no project field or filter, and MCP `list_projects` returns only project IDs and names alongside **a git clone URL with a credential embedded in it**. With no membership data, a project filter would match nothing, so the app should never call that tool ([09](09-verification-followups.md)). Font atlases, portraits, and talking sheets made on the website probably surface as untyped Creator gallery images, based on how the website code saves them ([09](09-verification-followups.md)). The live contract also drifts. The REST docs still say map objects auto-delete after 8 hours, while a months-old one still resolves. One tileset ID appeared in both MCP tileset lists, so tileset type should be decided by membership in the paged REST sidescroller list ([01](01-pixellab-api-asset-inventory.md); [R1](../reviews/R1-research-cross-review.md)).

The website is a Next.js app. Every app page sends signed-out visitors to `/signin?redirect=<path+query>` with the full query preserved. Whether login actually lands on the target is untested. Stable ID routes exist for characters (`/create-character/{id}`), objects (`/create-object/{id}`), top-down tilesets (`/maps/tilesets/{id}`), and Tiles Pro (`/maps/tiles/{id}`). Sibling research matched those IDs to public REST IDs, but that match dates from June 2026 and must be re-checked. Creator images have **no per-image URL**: `/create` reads only `tool` and `creatorCategory` ([03](03-pixellab-website-gallery-audit.md); [PixelLab docs](https://www.pixellab.ai/docs)). The `/editor?…&images=` route can preload an image into Pixelorama, but it is undocumented, desktop-only, and saves back into the real asset, so R1 cut it. The website's internal routes, such as `/creator/images` behind a Supabase session, are off limits: they are private, and a PixelLab maintainer has asked people not to automate them ([02](02-browser-integration-and-security.md); [R1](../reviews/R1-research-cross-review.md)).

## A full-access token, not CORS, sets the security envelope

Feasibility rests on live header captures. All 21 combinations of seven REST paths and three origins returned a 200 preflight that **reflects the request origin with `allow-credentials: true` and a 600-second preflight cache**. The edge cases matched, including `null`, `tauri://localhost`, and an arbitrary `https://evil.example`. Error responses carry ACAO too, so the app can read 401 and 404 bodies ([02](02-browser-integration-and-security.md)). R1 re-probed the API and backblaze and found the same behaviour ([R1](../reviews/R1-research-cross-review.md)). The catch is that **only `Content-Disposition` is in `Access-Control-Expose-Headers`**. Browser JavaScript therefore cannot read `Retry-After` on 423 or 429 responses, even though the OpenAPI says 423 carries it ([MDN Access-Control-Expose-Headers](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Expose-Headers)). Reflecting every origin is the kind of permissive setting that often gets locked down later. If that happens, the fallback order is: ask PixelLab, then a Tauri desktop wrapper, then a Worker proxy each user deploys themselves. A shared proxy that sees everyone's tokens is never acceptable ([02](02-browser-integration-and-security.md)).

The token is the real problem. The OpenAPI defines **one `HTTPBearer` scheme with no scopes**, and the account page's only control is "Generate new API key". That is the single revocation path, and whether it immediately invalidates the old key is unverified ([OpenAPI](https://api.pixellab.ai/v2/openapi.json); [Account page](https://www.pixellab.ai/account); [02](02-browser-integration-and-security.md)). A leaked token can spend credits, delete or retag the whole library, and reach Game Builder git, sandbox, and chat tools through MCP. A view-only app cannot shrink that blast radius; only scoped tokens from PixelLab can. The storage decision follows OWASP's advice to prefer `sessionStorage` when persistence is not needed ([OWASP HTML5 Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)). The token lives in memory, mirrored to `sessionStorage` by default. The copy says "this tab", not "until you close the browser", because session restore can keep it. **"Keep me signed in" (called "Remember on this device" in the research) is an off-by-default opt-in to `localStorage`** with a plain warning. The token field is a real password form so password managers can save and fill it, and the app shows only the last four characters. There is no "copy token" control, and the token is cleared everywhere on any 401 "Invalid API token". Passphrase encryption, `PasswordCredential`, and non-extractable `CryptoKey` obfuscation are cut: they protect only at rest, or not across browsers ([02](02-browser-integration-and-security.md); [R1](../reviews/R1-research-cross-review.md)).

The subtler threat is that **asset UUIDs work as bearer capabilities**. Character ZIPs, sprite sheets, tileset images, and MCP download helpers accept the bare UUID with no auth. Backblaze URLs embed the account ID plus the asset ID and never expire. **Rotating the token revokes none of them** ([MCP docs](https://api.pixellab.ai/mcp/docs); [02](02-browser-integration-and-security.md)). That fact reshapes three designs. First, deep links use an **opaque asset key** instead of the raw ID. The key is base64url(SHA-256(`type:uuid`)) truncated to about 12 characters, which is deterministic, cannot be reversed, and needs no mapping table. Spike 07's argument that "the fragment never reaches the server" ignores browser history sync, screenshots, copy-paste, and extensions. Second, **cache persistence follows the token mode**. In session mode the library stays in memory and the browser's HTTP cache. In Remember mode it goes to IndexedDB and the Cache API. A session-only token is hollow if a persisted cache holds every never-expiring URL. Third, "Forget key" clears the token, the library cache, and Cache API entries, and offers to keep folders and favorites, which are keyed by the opaque key. The copy notes that the browser's own HTTP cache can still hold images ([R1](../reviews/R1-research-cross-review.md)).

"View-only" has to be enforced mechanically, not by convention. A single fetch wrapper attaches `Authorization` only when the URL origin is exactly `https://api.pixellab.ai`. It refuses every method except GET on `/v2/*` and allows POST only to `/mcp` ([R1](../reviews/R1-research-cross-review.md)). The MCP client keeps an allowlist: `list_images`, `get_image` restricted to gallery refs, `list_maps`, `view_map`, and optional read-only getters such as `get_isometric_tile` and `get_tiles_pro`. Spike 09 adds a runtime gate on top. The app fetches `tools/list` once and calls only tools annotated `readOnlyHint: true`, so a future re-annotation by PixelLab cannot widen the app's reach ([09](09-verification-followups.md)). Two tools need special handling. **`get_map_object` is annotated not read-only** because it "retries saving finished pixels". Spike 01 had wrongly listed it among its read-only calls. The gallery does not need it, since map objects arrive through `list_objects` as one-direction objects. `get_image` is also annotated `readOnlyHint: false`, but its description ties the save retry to a completed *job* ID, and website-made gallery images have no job ([09](09-verification-followups.md)). R1 judged it safe for `gallery:` refs behind the regex `^gallery:(\d{13}|[0-9a-f-]{36})$`. Spike 09 notes the risk cannot be proven zero from outside. The Images chip therefore stays behind a clearly labelled setting until a Phase 0 check shows the gallery total, order, and top items unchanged after repeated reads ([R1](../reviews/R1-research-cross-review.md); [09](09-verification-followups.md)).

The remaining hygiene is standard but non-negotiable. The production CSP is served as a real HTTP header, not a `<meta>` tag, because meta CSP ignores `frame-ancestors` ([MDN CSP guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)). The exact header, as specified in design 05 §10.2, is:

```text
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' blob:; connect-src https://api.pixellab.ai https://backblaze.pixellab.ai; font-src 'self'; manifest-src 'self'; worker-src 'self'; base-uri 'none'; form-action 'none'; object-src 'none'; frame-ancestors 'none'
```

All art is fetched through `connect-src` and drawn on canvas, so `img-src` names no remote host. `connect-src` covers `backblaze.pixellab.ai` and `api.pixellab.ai`, including the no-auth MCP helper routes that serve tileset and isometric thumbnails ([09](09-verification-followups.md)). The CSP is paired with `Referrer-Policy: no-referrer`, `nosniff`, a `Permissions-Policy`, COOP and HSTS ([02](02-browser-integration-and-security.md); [R1](../reviews/R1-research-cross-review.md); design 05 §10.2). `data:` stays out because inline base64 becomes a `Blob` and then a `blob:` URL, and Vite's `assetsInlineLimit` is set to 0 ([Vite features](https://vite.dev/guide/features)). The S3 presigned host also stays out. Spike 09 suggested allowing it for display only, as a fallback for reading sheet geometry, but that is unnecessary while inline frames work. `style-src` without `'unsafe-inline'` should hold, because Svelte 5 transitions now use the Web Animations API ([sveltejs/svelte#6662](https://github.com/sveltejs/svelte/issues/6662)). Trusted Types became Baseline in February 2026, but whether Svelte runs under it is unverified ([MDN trustedTypes](https://developer.mozilla.org/en-US/docs/Web/API/trustedTypes)). The app never uses `{@html}`. It validates every URL taken from API or MCP text with `new URL()` and a host allowlist. ZIP entry names and download filenames are built only from slugged `[a-z0-9-]` names, which prevents ZIP-slip. There is no telemetry, analytics, error reporting, or CDN, and `connect-src` enforces that ([R1](../reviews/R1-research-cross-review.md)). Phishing clones on other origins cannot be prevented, because PixelLab accepts every origin. The mitigations are one canonical URL, open source, and advice to rotate the token after trying third-party tools. **ToS §2.2 asks anyone "building your own service" to contact PixelLab first.** That message should go out before public launch, and it should also ask about CORS stability, scoped tokens, exposing `Retry-After`, and read limits ([Terms of Service](https://pixellab.ai/termsofservice); [02](02-browser-integration-and-security.md)).

Networking has to assume the worst because PixelLab publishes no read limits. The OpenAPI declares 429 on only three GETs. An unauthenticated burst of 40 requests produced 40 × 401 and no rate-limit headers, which says nothing about authenticated limits. PixelLab's own website pages `/creator/images` at `limit=500`, which suggests bulk reads are tolerated ([09](09-verification-followups.md)). The plan uses one semaphore per host: four in flight to the API, dropping to two after any 429, and eight to media. Retries use full-jitter exponential backoff, because `Retry-After` is unreadable. A 401 halts everything and prompts for the token, a 423 means "still generating", and a 404 marks the asset deleted. In-flight GETs are deduplicated and cancelled with `AbortController` ([02](02-browser-integration-and-security.md)). R1 found a cost no spike had noticed: **every distinct authenticated REST URL pays its own preflight**, because the preflight cache is keyed per URL. Character detail should therefore load only when the viewer opens, never as a background prefetch. Media fetches must add no custom headers so they stay simple requests with no preflight ([R1](../reviews/R1-research-cross-review.md)). A full list sync of an account holding hundreds of each asset type takes about **10–30 REST requests** ([01](01-pixellab-api-asset-inventory.md)). The expensive parts are Creator thumbnails, which need one `get_image` per item, and maps, where tool descriptions warn that accounts reach four figures ([R1](../reviews/R1-research-cross-review.md)). Durable data also needs care. Safari deletes script-written storage after seven days of browser use without interaction. Storage eviction removes an origin's data all at once. Folders and favorites therefore need a versioned JSON export and import, alongside `navigator.storage.persist()` ([MDN storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria); [WebKit blog](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)).

## PixelLab's own gallery scatters assets across seven silos

The signed-in website could not be viewed live, so the audit read PixelLab's production JavaScript bundles directly. That yields strong code-level facts about labels, layout props, handlers, and query parsing, but not visual confirmation. Searches of Reddit, Product Hunt, Trustpilot, and AlternativeTo found no public reviews of PixelLab's asset management. Feedback likely lives in an inaccessible Discord ([03](03-pixellab-website-gallery-audit.md)). Even with that caveat, the evidence is consistent. **A user's assets live in at least seven separate libraries**: the Creator gallery, Characters, Objects, UI, Map Workshop (with Maps, Tilesets, and Tiles tabs), Create VFX, and Game Builder. The "Choose How You Want to Create" page presents them as separate products. There is no "all my assets" view and no cross-type search ([PixelLab select-interface](https://www.pixellab.ai/select-interface); [03](03-pixellab-website-gallery-audit.md)). Touch users get the worst of it. Character cards animate only when `hovered && visible`, at a fixed 5 fps. All four card actions (Add to project, Share, Export ZIP, Delete) sit in an overlay with `opacity: 0` and `pointerEvents: none` until hover, and the detail page literally says "Hover to download" ([03](03-pixellab-website-gallery-audit.md)). PixelLab's own docs say the Pixelorama editor that its "Edit" hand-offs open has "no support for mobile browsers" ([Ways to use PixelLab](https://www.pixellab.ai/docs/ways-to-use-pixellab)).

PixelLab also does several things worth keeping. `image-rendering: pixelated` appears throughout its bundles, and the Creator stage caps zoom with integer math. Its character exports are rich: a ZIP of all frames, a sprite sheet with JSON layout, Aseprite with tagged frames, a showcase GIF, and per-animation GIFs. Its filters match how game developers think: camera view, number of directions, canvas size, tags, and "untagged only". Its empty and no-match states are honest, for example "N images are hidden by the search or filters" with a one-click "Clear search & filters". Escape closes the preview, and deep links survive sign-in ([03](03-pixellab-website-gallery-audit.md)). The gallery should keep all of this and make it uniform across types. Two of PixelLab's habits should not carry over. Its "Copy agent reference" button and any "copy link" feature would leak the UUID capability, so the gallery offers only an explicit "Copy asset ID" inside collapsed raw details ([R1](../reviews/R1-research-cross-review.md)).

## Photo apps converged on two tabs after costly backlash

The clearest lesson from platform galleries is about structure, not polish. Apple's iOS 18 Photos merged everything into "one never-ending page" and removed tabs ([9to5Mac](https://9to5mac.com/2025/08/28/ios-26-fixed-the-photos-app-its-more-powerful-than-ever/)). It drew complaints in beta and after launch, and developers sold paid apps that recreated the old interface. A year later **iOS 26 restored separate Library and Collections tabs, with search as its own button** ([iMore](https://imore.com/apps/user-backlash-has-reportedly-caused-apple-to-rethink-ios-18s-photos-redesign); [TechCrunch](https://techcrunch.com/2025/06/09/after-user-backlash-apple-brings-back-tabs-to-the-photos-app-in-ios-26/); [MacRumors](https://macrumors.com/guide/ios-26-photos-app)). Google landed on the same shape, with a Photos / Collections / Search bottom bar. Google had earlier pulled a 2022 Library redesign after backlash ([Android Authority](https://www.androidauthority.com/google-photos-bottom-bar-redesign-3537107); [Droid Life](https://www.droid-life.com/2024/08/08/google-photos-introduces-collections-to-replace-library-tab/)). Muscle memory is fragile. An August 2026 bug that broke Google Photos' drag-to-select drew press coverage within days ([PhoneArena](https://www.phonearena.com/news/popular-google-photos-feature-goes-missing_id182462); [Android Authority](https://www.androidauthority.com/google-photos-drag-to-select-fixed-3697467/)). Amazon's May 2026 redesign moved the grid behind a memories carousel ([9to5Google](https://9to5google.com/2026/05/05/amazon-photos-app-redesign/)), which is the wrong model for a working tool. The takeaway is to ship few controls, keep them in fixed homes, and put the grid one tap away ([04](04-platform-gallery-apps-ux.md)).

Grid layout is where pixel art departs from photos. Square-crop grids cut off sprites, and Apple's own square grid crops thumbnails ([Apple Community](https://discussions.apple.com/thread/256038315)). Justified rows give a 16×16 icon next to a 512×288 map wildly varying row heights. Masonry breaks focus and reading order for keyboard and magnifier users ([CSSWG #5675](https://github.com/w3c/csswg-drafts/issues/5675)), and in 2026 only Safari ships native support ([OpenReplay](https://blog.openreplay.com/css-grid-lanes-masonry-layout/)). Every spike converged on **uniform square cells that fit the whole asset without cropping** ([04](04-platform-gallery-apps-ux.md); [05](05-creative-asset-gallery-ux.md)). Uniform cells also make virtualization pure arithmetic. Google Photos' web grid kept "never more than 50 photos" in the DOM ([2018 write-up](https://steemit.com/art/@whatspal/buildingthegooglephotoswebui-sinr80fhdv)), and Lighthouse flags documents beyond about 1,400 nodes ([Chrome Lighthouse](https://developer.chrome.com/docs/lighthouse/performance/dom-size)). Density comes in discrete steps, like Samsung's five pinch levels and Windows Photos' S/M/L ([SlashGear](https://www.slashgear.com/1623030/samsung-galaxy-gallery-apps-features); [Technipages](https://www.technipages.com/windows-11-how-to-change-image-thumbnail-size)). Discrete steps also keep pixel scaling whole. In a browser, Ctrl/Cmd +/- must stay page zoom.

Interaction grammar is settled across platforms. On touch, long-press selects and a visible Select button serves as the fallback. On desktop, click, Shift-click, Cmd/Ctrl-click, and Cmd-A follow the macOS model ([Apple keyboard shortcuts in Photos](https://support.apple.com/guide/photos/pht9b4411b24/mac); [Popular Science](https://www.popsci.com/diy/select-multiple-photos-ios-android/)). The viewer swipes between items and closes on swipe-down or Esc. For accessibility it is a modal dialog that traps focus and returns it to the thumbnail ([W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)), and the browser Back button closes it ([NN/g](https://www.nngroup.com/articles/overuse-of-overlays/)). Albums work as references, not copies. Windows File Explorer Gallery removing a source deletes nothing ([Pureinfotech](https://pureinfotech.com/add-remove-folders-gallery-file-explorer-windows-11/)). That maps directly onto local folders over remote PixelLab IDs ([04](04-platform-gallery-apps-ux.md)).

Creative and AI-asset tools add the organization and export layer. Midjourney's web app separates Create from Organize. Its folders allow membership in several folders at once, can be grouped, and download as a whole ([Midjourney updates](https://updates.midjourney.com/new-tools-for-organization/)). Scenario collections group assets without owning them, so deleting a collection leaves the assets alone ([Scenario help](https://help.scenario.com/en/articles/collections)). **Bulk download is the most-requested missing feature across AI tools.** Recraft's request stayed open from August 2024 until November 2025. Leonardo users buy third-party Chrome extensions to get it. Adobe CC Libraries users have asked since 2019 ([Recraft feedback](https://feedback.recraft.ai/feature-requests/p/bulk-image-download); [Gumroad listing](https://acepter.gumroad.com/l/Leonardoaibulkdownloader); [Adobe community](https://community.adobe.com/questions-606/how-to-bulk-download-images-within-libraries-to-my-computer-579733)). Recraft also names ZIPs after the project, so "Untitled" projects produce useless filenames ([Recraft feedback](https://feedback.recraft.ai/feature-requests/p/bulk-image-download)). Firefly documents bulk selection on mobile but not on the web, an avoidable parity gap ([Adobe Firefly web](https://helpx.adobe.com/firefly/web/access-your-files/view-generation-history.html)). Eagle puts its inspector in a right-side panel ([Eagle support](https://en.eagle.cool/support/article/interface-inspector)). A reported Raindrop re-import flattened every collection into one, which shows that organization import must preserve structure ([WorldBrain community](https://community.worldbrain.io/t/raindrop-io-import-retain-collection-structure/936)). Server-side caps define the upper bound: Drive splits archives into 2 GB parts, and Dropbox refuses ZIPs over 250 GB or 10,000 files ([Google Workspace blog](https://workspaceupdates.googleblog.com/2016/08/improvements-to-downloading-files-and-folders-in-Drive.html); [Dropbox help](https://help.dropbox.com/desktop-web/download-entire-folders)) ([05](05-creative-asset-gallery-ux.md)).

R1 turned these patterns into one interaction model. Its biggest call settles the animated-preview debate. Lists carry no frames, so autoplaying a 50-card screen would cost about **50 detail calls plus hundreds of frame GETs** against unpublished limits. R1 therefore made thumbnails **static by default** ([R1](../reviews/R1-research-cross-review.md)). The final design instead turns Play previews **on by default with caps**: in view only, at most 8 playing, one low-priority detail fetch at a time, and off under reduced motion or Save-Data (ruling F-9). The default is a build flag that ships off if Phase 0 finds any read cost or a 429 at concurrency ≤ 2 (E-9).

## Whole device pixels keep every sprite crisp

One rendering rule covers every engine: **`image-rendering: pixelated`, an integer scale computed in device pixels, and sizing through `width`/`height` only**. `pixelated` has shipped in Chrome 41, Firefox 93, and Safari 10. Unprefixed `crisp-edges` reached Chrome only in version 148. The spec allows both values to smooth at non-integer factors ([BCD image-rendering](https://github.com/mdn/browser-compat-data/blob/main/css/properties/image-rendering.json); [CSS Images 3](https://drafts.csswg.org/css-images-3/#the-image-rendering)). The old two-declaration fallback, born when Chrome had only `pixelated` and Firefox only `crisp-edges`, is now dead weight ([06](06-pixel-art-rendering-animation-and-export.md)). Safari forces the second half of the rule. **It ignores `pixelated` when a CSS transform scales an element or any ancestor** ([WebKit 185683](https://bugs.webkit.org/show_bug.cgi?id=185683)). It also ignores it on tiled backgrounds ([WebKit 177037](https://bugs.webkit.org/show_bug.cgi?id=177037)) and on background images of any element with a border ([WebKit 289023](https://bugs.webkit.org/show_bug.cgi?id=289023)). So art is never scaled with `transform`, `zoom`, `object-fit`, or `background-image`. R1 chose this strict rule over spikes that proposed `object-fit: contain`, because a box that is not an exact multiple of the art silently produces a fractional scale ([R1](../reviews/R1-research-cross-review.md)).

Fractional device-pixel ratios are solved by making the device-pixel count, not the CSS scale, the integer. At DPR 1.5, a 32 px sprite with k = 3 is 96 device pixels and 64 CSS pixels, and it renders perfectly evenly ([MDN crisp pixel art](https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look)). Layout recomputes on DPR changes, such as browser zoom or moving to another monitor, using MDN's `matchMedia` resolution pattern ([MDN devicePixelRatio](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio)). Safari cannot report exact device-pixel boxes, so the formula is the portable path ([web.dev device-pixel-content-box](https://web.dev/articles/device-pixel-content-box)). When an asset is larger than its cell (k < 1), as with maps, big Creator images, and tall sheets, the whole asset is downscaled smoothly and marked "fit". It is never cropped, and never nearest-neighbour downscaled, because that "will skip every second pixel" ([CSS Images 3](https://drafts.csswg.org/css-images-3/#the-image-rendering)). PixelLab character canvases are much larger than the character: v3 canvases at size 48 measured 84×84 and 92×92. Static thumbnails of characters and objects are therefore trimmed to their alpha bounding box and bottom-aligned so feet line up across a row. Tilesets show the sheet exactly as returned and are never re-sorted ([06](06-pixel-art-rendering-animation-and-export.md); [R1](../reviews/R1-research-cross-review.md)).

Backdrops matter more than chrome for judging pixel art. Color-critical work uses an achromatic surround, typically Munsell N7 or N8, because tinted or extreme surrounds bias perception ([rpimaging](https://www.rpimaging.com/munsell-neutral-gray-paint.html); [greynotgrey](https://greynotgrey.com/blog/2012/05/07/colour-theory-monday-when-is-grey-not-grey/)). R1 picked spike 08's position. The grid uses the theme surface, since a checkerboard competes with 16–32 px sprites. The viewer puts five backdrops behind one Backdrop button: Theme, Checker, Light gray (N8), Mid gray (N5) and Black (ruling F-4; white was dropped), as one global setting with a per-session override. The stage has exactly zero chroma, and the checker is drawn with a CSS conic gradient. Vector painting sidesteps Safari's tiling bug, and `forced-color-adjust: none` keeps the stage intact under forced colors ([R1](../reviews/R1-research-cross-review.md); [MDN forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors)).

Animation runs on canvas from one shared `requestAnimationFrame` ticker that plays a `durations[]` array in milliseconds. Uniform fps is just a filled array. The ticker is time-based, so 60 Hz and 144 Hz displays play at the same speed. It clamps large deltas after tab switches and pauses on `visibilitychange` ([MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame); [06](06-pixel-art-rendering-animation-and-export.md)). Each canvas keeps the art's native resolution, with CSS doing the integer upscale. `imageSmoothingEnabled = false` must be reset after every resize, because assigning canvas dimensions resets the context ([HTML spec](https://html.spec.whatwg.org/multipage/canvas.html#concept-canvas-set-bitmap-dimensions)). CSS `steps()` sprite animation is rejected. It needs `background-image`, which runs into the Safari bugs, and it cannot express per-frame timing or scrubbing. Memory is the real budget. A 64×64 frame decodes to 16 KB, so an 8-direction character with ten 9-frame animations is about **11.5 MB decoded**. Bitmaps load only for visible or open players and sit in a byte-capped LRU that calls `close()` on eviction ([06](06-pixel-art-rendering-animation-and-export.md)). The player defaults to **8 fps** with a per-animation override stored locally, labelled "timing not provided by PixelLab". Its controls are play/pause, frame step, a frame filmstrip (which replaced the range scrubber; ruling F-4), speed, loop/once, a compass direction picker, and a state switcher ([09](09-verification-followups.md); [R1](../reviews/R1-research-cross-review.md)). The grid-to-viewer transition is a plain opacity crossfade. View-transition snapshots are rasters, a WebKit bug reports blurry captures of transformed elements, and no source confirms that `pixelated` applies to `::view-transition-*` ([WebKit 317712](https://bugs.webkit.org/show_bug.cgi?id=317712); [06](06-pixel-art-rendering-animation-and-export.md)).

Exports start from one fidelity rule: **1× always serves the original PNG bytes, never a canvas re-encode**. Converting to and from premultiplied alpha is lossy for semi-transparent pixels ([HTML spec pixel manipulation](https://html.spec.whatwg.org/multipage/canvas.html#pixel-manipulation)). Larger scales use integer nearest-neighbour in an `OffscreenCanvas` worker, which is supported in every 2026 target from Safari 16.4 ([BCD OffscreenCanvas](https://github.com/mdn/browser-compat-data/blob/main/api/OffscreenCanvas.json)).

| Output | Rule |
|---|---|
| PNG 1× / N× | Original bytes at 1×; 2/4/8× nearest-neighbour with smoothing off; check the iOS canvas area cap before drawing |
| Sprite sheet | PixelLab's own layout: uniform cell sized to the largest frame, frames centred and never rescaled, row 0 holds rotations, then one row per animation × direction, frames as columns, no power-of-two padding ([OpenAPI](https://api.pixellab.ai/v2/openapi.json)) |
| Sheet JSON | One format: Aseprite JSON hash, field names verified in [Aseprite's exporter](https://github.com/aseprite/aseprite/blob/main/src/app/doc_exporter.cpp), plus an `animations` map in the shape PixiJS reads; no engine-compatibility claims in v1 |
| GIF | `gifenc`; exact palette when ≤255 colours; transparent index 0; disposal 2; **cumulatively rounded centisecond delays of at least 2 cs**, because browsers turn ≤10 ms into 100 ms ([WebKit r73295](https://trac.webkit.org/r73295)); Matte or Threshold mode for semi-alpha; default scale is the smallest k that makes the long side ≥256 px |
| Frames | PixelLab's ZIP layout: `rotations/{dir}.png`, `animations/{anim}/{dir}/frame_000.png` |
| Single-asset ZIP | Official character ZIP or sprite sheet passed through untouched; object sprite sheet fetched with the bearer token |
| Bulk ZIP | `client-zip` in store mode; `{type}/{slug}--{key}/…` paths; a root `manifest.json` listing sources and any failures |
| Cut | APNG, animated WebP, Godot/Unity/TexturePacker formats, a naming-template editor |

Sources for the table: [06](06-pixel-art-rendering-animation-and-export.md) and [R1](../reviews/R1-research-cross-review.md).

Delivery uses feature detection and is engineered for iOS. Streaming straight to disk through `showSaveFilePicker` works in Chromium desktop 86+ and Chrome Android 132+. Firefox and Safari get an in-memory `Blob` and `<a download>`. iOS 14+ and Android Chrome add a share sheet for "Save to Photos/Files" ([06](06-pixel-art-rendering-animation-and-export.md); [W3C Web Share](https://www.w3.org/TR/web-share/)). Browsers gate multiple automatic downloads ([How-To Geek](https://www.howtogeek.com/428416/how-to-enabledisable-multiple-file-downloads-in-chrome/)), so multi-file output always becomes one ZIP. The share sheet and the picker both consume transient user activation ([WebKit User Activation API](https://webkit.org/blog/13862/the-user-activation-api/)), so long downloads use a two-step flow: build the file, then save it from a "Your file is ready" sheet (02 S11). On iOS, community reports put the canvas cap at **16,777,216 px of area and 224–384 MB of total canvas memory** ([pqina](https://pqina.nl/blog/canvas-area-exceeds-the-maximum-limit/); [Apple forums](https://developer.apple.com/forums/thread/687866)). An 8-direction, 16-frame sheet of 128 px cells at 8× is about 134 million pixels, far over that cap, so exports check `w × h × k² ≤ 16,777,216` and fall back to a lower scale with a notice. Non-streaming ZIPs split into numbered parts above a tunable cap, starting at 300 MB on iOS and 1 GB on desktop; the design closes each part at an asset boundary by a running byte count rather than a `predictLength` estimate (B-6) ([06](06-pixel-art-rendering-animation-and-export.md); [client-zip](https://github.com/Touffy/client-zip)). R1 resolved one trap. `client-zip` cannot read ZIPs, so bulk exports rebuild PixelLab's character layout client-side from frame URLs instead of nesting official ZIPs or adding an unzip library ([R1](../reviews/R1-research-cross-review.md)).

## Four runtime libraries and one quiet theme cover the build

Plain **Vite 8** is the right base today. It has been stable since 2026-03-12, with Rolldown as its only bundler ([Vite 8 announcement](https://vite.dev/blog/announcing-vite8)). Vite+ is now MIT-licensed and reached 1.0 on 2026-09-28. It builds Svelte apps, wraps the same Vite 8.3.4, and adds Oxlint, Oxfmt, Vitest, and a `vp` CLI ([viteplus.dev](https://viteplus.dev/guide); [InfoQ](https://infoq.com/news/2026/10/cloudflare-viteplus-stable)). A local smoke test showed its gaps. **`vp lint` reported nothing for an unused variable in a `.svelte` script, and `vp fmt` skipped `.svelte` files entirely.** One combined npm install also silently resolved a pre-1.0 `vite-plus@0.3.3` ([07](07-tech-stack-and-architecture.md); [Oxc formatter docs](https://oxc.rs/docs/guide/usage/formatter/language-support.html)). Svelte projects on Vite+ would still need `svelte-check` and Prettier, so its "one CLI" benefit is partial. Because it reads the same `vite.config.ts`, migrating later costs nothing. Svelte 5.57.2 provides stable runes, snippets, attachments (5.29+), and `createContext` (5.40+). Component-level `await` remains experimental until Svelte 6, so v1 avoids it ([Svelte await docs](https://svelte.dev/docs/svelte/await-expressions)). Asset arrays should use `$state.raw` to avoid deep proxies over thousands of read-only records ([Svelte $state docs](https://svelte.dev/docs/svelte/$state)). **TypeScript must be pinned to `~6.0.3`**: `typescript@latest` is now 7.0.2, and svelte-check supports TS 7 only through an opt-in dual install ([svelte-check README](https://unpkg.com/svelte-check@4.7.6/README.md)).

| Concern | Choice | Reason |
|---|---|---|
| Build and UI | Vite 8.3.4, Svelte 5.57.2, `@sveltejs/vite-plugin-svelte` 7.3.1 | A minimal app measured 15.5 KB gzip |
| Types and lint | `svelte-check` 4.7.7, Prettier with `prettier-plugin-svelte` | Svelte a11y and compiler warnings; Oxlint has no `.svelte` diagnostics yet |
| Routing | ~25-line hash router | Works on any static host with no fallback config |
| Persistence | `idb-keyval` 6.3.0 (0.6 KB) for org data and snapshots; Cache API for image bytes; `localStorage` for theme, backdrop, and zoom | Filtering happens in memory; preferences need a synchronous read before first paint |
| Grid | Hand-rolled row windowing over uniform cells | Pure arithmetic, no item measurement; `virtua` is the fallback |
| Primitives | `<dialog>`, `popover`, invoker commands, anchor positioning with an `@supports` fallback, `<input type=range>` | All Baseline; Bits UI is the fallback for complex widgets |
| Styling | Plain CSS: `@layer`, nesting, OKLCH, `light-dark()`, container queries | All Baseline in 2026; no Tailwind toolchain |
| Icons and type | `@lucide/svelte` deep imports; `system-ui` and `ui-monospace` stacks | ~0.4 KB per icon, filled heart and star for on-states; 0 KB of fonts, CSP-clean |

The architecture has one separation rule: views never call `fetch`. Only `lib/api` (REST wrapper, MCP client, pool, `normalize.ts`) touches the network. Only `lib/storage` touches IndexedDB or the Cache API. Module-level rune stores orchestrate the two, which is safe because there is no SSR ([Svelte context docs](https://svelte.dev/docs/svelte/context); [07](07-tech-stack-and-architecture.md)). The budget is **≤60 KB gzip of initial JS** (design 05 §11.4; research 07 proposed 50 KB), enforced by a CI script. The runtime set is about 17–20 KB plus app code, against the roughly 530 KB `/create` chunk on PixelLab's own site ([07](07-tech-stack-and-architecture.md); [03](03-pixellab-website-gallery-audit.md)). In Remember mode, startup renders from the cached snapshot and then syncs in the background. In session mode, every visit re-syncs the lists. R1 left open whether a progress skeleton is enough for that cost ([R1](../reviews/R1-research-cross-review.md)).

The visual direction is spike 08's **"Quiet Studio"** (refined into "Quiet Studio, lifted" by ruling F-3), the only theme, with light, dark, and system modes. It fits where design moved in 2025–2026. Linear's 2026 refresh dimmed navigation, removed colored icon backgrounds, and moved to warmer, less saturated grays ([Linear](https://linear.app/now/behind-the-latest-design-refresh)). Apple tells designers to keep control color "judicious" so content shines through ([Apple Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/liquid-glass)). NN/g documented how translucent chrome over busy content hurt legibility in iOS 26 ([NN/g](https://www.nngroup.com/articles/liquid-glass/)). Google's Material 3 Expressive research spanned 46 studies and 18,000+ participants. It found key actions spotted up to **4× faster** when emphasized, and also that breaking familiar patterns hurt usability and a strong minority preferred calmer designs ([Google Design](https://design.google/library/expressive-material-design-google-research)). The gallery therefore uses OKLCH tokens wired through `light-dark()` and `color-scheme` ([MDN light-dark](https://developer.mozilla.org/docs/Web/CSS/color_value/light-dark)). Chrome neutrals keep chroma ≤0.006 and the art stage has exactly zero. There is one ice-blue accent, used only for selection, focus, the primary action, and active navigation, and it must be checked against PixelLab's brand colors, which have not been audited. Hierarchy comes from tonal surfaces rather than borders. **Bars are opaque**, because Safari does not expose `prefers-reduced-transparency` ([caniuse](https://caniuse.com/wf-prefers-reduced-transparency)). Hover never scales a card, because scaling blurs pixel art. The wordmark is an inline SVG drawn on a pixel grid rather than a pixel webfont ([08](08-visual-design-theming-responsive.md); [R1](../reviews/R1-research-cross-review.md)). Spike 08 computed its contrast ratios itself, so they must be re-checked in a contrast tool before the tokens are frozen.

Accessibility and responsiveness are part of the spec, not a later pass. The baseline is WCAG 2.2 AA ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). Under 2.5.7, every drag has a single-pointer alternative, such as "Add to folder…" and buttons for every swipe. Under 2.5.8, targets are at least 24 px, with a 44 px policy on touch. Under 2.4.11, `scroll-padding` keeps sticky bars from covering focus. 2.2.2 is met through the preview toggle and 2.1.4 through the shortcut switch. Focus uses outlines that survive forced colors, and reduced motion turns transitions into cuts ([08](08-visual-design-theming-responsive.md); [W3C What's new in 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/)). The fluid type scale keeps max/min at or below 1.5 so text still reaches 200% zoom, because `vw`-driven `clamp()` can fail WCAG 1.4.4 ([Adrian Roselli](https://adrianroselli.com/2019/12/responsive-type-and-zoom.html)). The shell changes at 600, 840, 1200, and 1600 CSS px, following Android's window size classes, plus a `max-height: 480px` rule for landscape phones. It uses `svh` for the shell, `dvh` only for the fullscreen viewer and sheets, and safe-area padding on edge-anchored bars ([Android window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes); [web.dev viewport units](https://web.dev/blog/viewport-units)). Foldable viewport segments are Chromium-only and deferred ([Chrome](https://developer.chrome.com/blog/viewport-segments-api-shipped)). For branding, spike 08 advises against "PixelLab" as the leading word of the product name. It recommends an unofficial disclaimer on the connect screen and in the README, and never borrowing PixelLab's logo or colors ([08](08-visual-design-theming-responsive.md)). The final name is the user's decision.

## Conclusion

The research inverts the expected risk profile. Browser access, pixel-crisp rendering, and client-side export, the parts that look hardest, are solved with platform features and roughly 7 KB of lazy libraries. The hard problems come from PixelLab's API shape. **Because UUIDs are permanent download keys, a privacy rule becomes an architecture rule**: it dictates hashed routes, cache persistence tied to the token mode, slugged export paths, and a Forget flow that clears more than the token. Because frames exist only in detail responses, the network cost decides the UX: grid previews play only under hard caps, and details load only on demand. Because two families depend on MCP prose with no output schema, the app should treat Images and Maps as degradable sources behind one parser module. In practice the core gallery is the seven REST families, and the MCP families are the parts most likely to break first.

The strategic implication is that the gallery's advantage is structural rather than cosmetic. It offers one library, one search, uncapped cross-type export with metadata, and working touch parity. PixelLab's site lacks all four, and leading AI tools took more than a year to ship bulk download. The two remaining dependencies sit outside the code. One half-day of tokened Phase 0 measurement decides concurrency defaults, CSP hosts, and whether Images ships on by default. One message to PixelLab, covering ToS §2.2, CORS stability, and scoped tokens, decides whether the backendless design stays viable at public launch. Phase 0 should land before any code depends on its results (work that needs none of them may start earlier; ruling B-1), and the PixelLab answer before public launch (D31).
